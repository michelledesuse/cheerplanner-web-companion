# RCA — CheerPlanner SMS broadcast: every FIRST send shows recipients "Failed", "Resend to failed" works

**App:** spirit-finance-2 (CheerPlanner) · **Run:** 49a16ce2-4841-43ee-84ad-acd519bc38d9 · **Prod DB:** spirit-finance-2-test_database
**Verdict:** Source bug — thread-unsafe lazy init of the Twilio client in `backend/core/sms.py`. Not a Twilio/account problem, not a secret problem, not infra.

---

## Symptom
On the live app, the FIRST `POST /api/team/broadcast/send` after the backend pod (re)starts reports nearly all recipients as **Failed** and no texts arrive. Tapping **Resend to failed** (`POST /api/team/broadcast/{id}/resend-failed`) a few seconds later succeeds and every text is delivered.

## What the production data shows

**broadcast `5dCSwahE4SXY`** (created `2026-11-08T03:00:36.323Z`, 22 recipients):
- `sms_messages` (direction=out) for this broadcast = 22 docs, ALL created at `03:00:36.291`.
- Exactly **1** doc has `updated_at == created_at == 03:00:36.291` → sid `SM8fcdd9ef…` (to `+17604844188`). This is the only message that went out on the first send (matches the single log line `03:00:44`? no — `03:00:36.290 - core.sms - SMS sent sid=SM8fcdd9ef… attempt=1`).
- The other **21** docs have `updated_at = 03:00:44–45` → they were only sent ~8s later, during `resend-failed` (log: `POST …/5dCSwahE4SXY/resend-failed 200 OK` at 03:00:44).
- **Critically: every `sms_messages` doc has `error_code = null` and `error_message = null`, including the 21 that "failed."**

Same pattern on the prior broadcast `VmcGbshdxid1` (2026-11-07T17:16): single first-send message, then a `resend-failed` burst at 17:16:12 that delivered the rest.

(The broadcast docs themselves now show `failed:0, failed_targets:[], retried_count:0` because the resend overwrote the failure counters after it succeeded.)

## Why this is decisive
A real Twilio rejection ALWAYS carries an `error_code` (e.g. 21211 invalid number, 21610 opted-out, 20429 rate-limit). The 21 "failed" recipients have **no error_code and no error_message** → **they never reached Twilio at all**. The `twilio.http_client` logs confirm it: at `03:00:36` there is a single Twilio API request/response; the bulk burst of ~21 `BEGIN Twilio API Request` / `Response Headers` lines all happen at `03:00:44` (the resend). There are **no** `send_sms failed` / `send_sms retrying` / `Twilio client init failed` / `Twilio not configured` lines anywhere in the last 24h — the failures were completely silent.

## Root cause (confirmed by reading the source at `/app/scratch/backend/core/sms.py`)

```python
_client = None
_client_init = False

def _get_client():
    global _client, _client_init
    if _client_init:
        return _client
    _client_init = True          # (1) flag set BEFORE the client is built
    sid = os.getenv("TWILIO_ACCOUNT_SID")
    token = os.getenv("TWILIO_AUTH_TOKEN")
    if not sid or not token:
        logger.info("Twilio not configured — SMS disabled")
        _client = None
        return None
    try:
        from twilio.rest import Client
        from twilio.http.http_client import TwilioHttpClient
        http = TwilioHttpClient(timeout=20)
        _client = Client(sid, token, http_client=http)   # (2) assigned AFTER the flag
    except Exception as exc:
        logger.warning("Twilio client init failed: %s", exc)
        _client = None
    return _client
```

This is a classic check-then-set **race condition**, and it is not thread-safe. Broadcasts are dispatched concurrently — the file defines `_SEND_CONCURRENCY = 5` and the comment states sends run on a threadpool. On the very first broadcast after a pod start:

1. The winning worker thread sees `_client_init == False`, sets `_client_init = True`, then spends real time doing `from twilio.rest import Client` + constructing the HTTP client + `Client(...)`.
2. During that window, the other worker threads churn through the remaining recipients, see `_client_init == True`, and immediately `return _client` — which is **still `None`** because step (2) hasn't completed.
3. In `send_sms_ex`, `if not client or not from_number: return None` fires → the recipient is marked failed **with no Twilio call and no error_code**, and because it returns before `_send_one_detailed`, the `_MAX_SEND_ATTEMPTS = 3` retry/backoff logic is **bypassed entirely**.
4. The winning thread finishes, `_client` is now real, and its single message sends — hence exactly **1 of 22** succeeds on the first send.
5. By the time the user hits Resend (~8s later) `_client` is fully populated, so all 21 succeed. The init happens once per process, so the bug reproduces once per pod lifetime (first broadcast after each restart) — exactly the reported behavior.

Secondary latent defect: the "no sid/token" and "init failed" branches set `_client = None` **and leave `_client_init = True`**, so a genuinely-missing/transient first init is **cached as None forever** for the life of the pod (the "caches None forever" concern). Env vars are fine here, so this isn't the active cause — but the same function should not poison itself on a transient failure.

`TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_PHONE_NUMBER` are all **present and non-empty** on the live run. Credentials are correctly configured — not the cause.

## Suggested fix (`backend/core/sms.py`, `_get_client`)
Make initialization thread-safe with double-checked locking, publish the flag **only after** the client is assigned, and do **not** cache a None result from a missing-config / failed init:

```python
import threading
_client = None
_client_init = False
_client_lock = threading.Lock()

def _get_client():
    global _client, _client_init
    if _client_init:
        return _client
    with _client_lock:
        if _client_init:            # double-checked: another thread may have finished
            return _client
        sid = os.getenv("TWILIO_ACCOUNT_SID")
        token = os.getenv("TWILIO_AUTH_TOKEN")
        if not sid or not token:
            logger.info("Twilio not configured — SMS disabled")
            return None             # do NOT set _client_init → allow a later retry
        try:
            from twilio.rest import Client
            from twilio.http.http_client import TwilioHttpClient
            http = TwilioHttpClient(timeout=20)
            client = Client(sid, token, http_client=http)
        except Exception as exc:    # noqa: BLE001
            logger.warning("Twilio client init failed: %s", exc)
            return None             # don't cache the failure
        _client = client
        _client_init = True         # publish flag ONLY after _client is set
        return _client
```

The lock serializes only the one-time construction (the Twilio client itself is safe to share across threads), so there is no ongoing throughput cost. After this change, concurrent threads on the first broadcast block briefly until the client exists, then all get a valid client — no more silent null-client failures. Optionally, also treat a `None` client in `send_sms_ex` as a retryable condition so the existing `_MAX_SEND_ATTEMPTS` backoff can cover any residual edge.
